# Ballerina HTTP Library

## Overview

This module provides the HTTP client and listener APIs for building and consuming HTTP services. The full jBallerina `http` module covers two sides:

**Client** — response data binding to custom types and status code records, authentication (Basic, Bearer, JWT, OAuth2), resiliency patterns (circuit breaker, retry, failover, load balancer), cookie management, HTTP response caching, compression negotiation, connection pooling, async requests, HTTP/2 server push, Server-Sent Events, multipart payloads, and streaming I/O.

**Service / Listener** — an HTTP listener with configurable host, TLS, HTTP version, and request limits; service definition with path-based routing and resource function dispatch; automatic binding of path parameters, query parameters, headers, and payloads in resource signatures; caller-based response dispatch; request/response interceptor pipeline; service-level and resource-level annotations (`@http:ServiceConfig`, `@http:ResourceConfig`, `@http:Payload`, `@http:Header`, `@http:Query`, `@http:Cache`); CORS configuration; listener authentication and authorization (File user store, LDAP, JWT, OAuth2); status code response types from resources; and SSE streaming responses.

The Go Native Interpreter supports the **HTTP client subset**: the nine core remote methods (including `forward`), the client resource access syntax (`client->/albums/[id]`) for all seven accessors, TLS/mTLS (PEM-based), redirect following, connection pooling, and both manual payload extraction and automatic response data binding to the contextually expected type. It also supports a native **listener**: creating an `http:Listener`, attaching and detaching services, and starting and stopping it (`'start`, `gracefulStop`, `immediateStop`); attached services are dispatched by path-based routing to resource functions. See the Listener and Service tables below for the current support status of listener configuration, TLS, and broader service-side features.

## Key Functionalities

- Send HTTP requests using GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS, and custom verbs.
- Address a resource with the client resource access syntax (`client->/albums/[id].put(payload)`), passing query parameters as named arguments.
- Forward inbound requests to upstream services preserving method, headers, and body (`forward`).
- Configure request timeout, HTTP version (1.1/2.0), redirect behaviour, connection pool settings, and compression negotiation.
- Secure connections with TLS and mutual TLS using PEM certificate and key files.
- Set custom request headers and override the inferred Content-Type.
- Read the response status code, text, JSON, or binary payload.
- Bind the response payload directly to the expected type — records, arrays, maps, `json`, `string`, `byte[]`, and their nilable forms — driven by the response `Content-Type`.
- Inspect response headers by name or enumerate all header names.
- Bind query parameters, `@http:Header` parameters, an `http:Headers` parameter, and `@http:Payload` (or default payload) parameters in resource function signatures.
- Run request interceptors before the resources of an `http:InterceptableService` and pass data to them through `http:RequestContext`.
- Configure a service with `@http:ServiceConfig`: host-based dispatch, `treatNilableAsOptional`, `laxDataBinding`, a `mediaTypeSubtypePrefix` for response media types, and response `compression` and `chunking`.
- Construct `Response` objects in resource functions and populate them with `setTextPayload`, `setJsonPayload`, `setBinaryPayload`, `setHeader`, and direct field assignment (`response.statusCode = 404`).
- Construct outbound `Request` objects and populate them for forwarding.
- Set a request or response body generically via `setPayload`, dispatched by the runtime type of the value.
- Decode an `application/x-www-form-urlencoded` request body into a parameter map via `getFormParams`.
- Set and extract multipart request/response bodies as `mime:Entity[]` via `setBodyParts`/`getBodyParts`.
- Parse structured header values (value + parameter map) with the header parsing utility.

## Examples

```ballerina
import ballerina/http;
import ballerina/io;

public function main() returns error? {
    // Plain HTTP client with a 10-second timeout and custom pool settings
    http:Client httpClient = check new ("http://httpbin.org", {
        timeout: 10,
        poolConfig: {maxIdleConnections: 50}
    });

    // GET request
    http:Response getResp = check httpClient->get("/get");
    io:println("Status: ", getResp.statusCode);
    json body = check getResp.getJsonPayload();
    io:println("Body: ", body);

    // POST request with a JSON payload
    json payload = {name: "Alice", age: 30};
    http:Response postResp = check httpClient->post("/post", payload);
    io:println("POST status: ", postResp.statusCode);

    // Client resource access syntax: path segments and query parameters.
    // The payload binds to the expected type, as with the remote methods.
    http:Response albumResp = check httpClient->/albums/[42]/tracks;
    io:println("Resource status: ", albumResp.statusCode);

    json album = check httpClient->/albums/[42];
    io:println("Album: ", album);

    http:Response searchResp = check httpClient->/albums(genre = "rock", 'limit = 10);
    io:println("Search status: ", searchResp.statusCode);

    http:Response createResp = check httpClient->/albums.post({name: "Kind of Blue"});
    io:println("Created: ", createResp.statusCode);

    // Forward an inbound request to an upstream service
    http:Request req = new;
    req.method = "PUT";
    req.setJsonPayload({id: 1, data: "updated"});
    http:Response fwdResp = check httpClient->forward("/resource/1", req);
    io:println("Forward status: ", fwdResp.statusCode);

    // TLS client with a custom CA certificate
    http:Client secureClient = check new ("https://example.com", {
        secureSocket: {cert: "/path/to/ca.pem"}
    });
    http:Response secureResp = check secureClient->get("/");
    io:println("Secure status: ", secureResp.statusCode);
}
```

A service binds path, query, header, and payload parameters from the resource signature, and the return value becomes the response:

```ballerina
import ballerina/http;
import ballerina/io;

type Album record {|
    string title;
    string artist;
|};

final map<Album> albums = {};

service /albums on new http:Listener(9090) {
    // GET /albums?artist=Miles%20Davis — `artist` is an optional query parameter.
    resource function get .(string? artist) returns Album[] {
        return from Album album in albums
            where artist is () || album.artist == artist
            select album;
    }

    // GET /albums/kind-of-blue — `id` is a path parameter; a missing album is a 404.
    resource function get [string id]() returns Album|http:Response {
        Album? album = albums[id];
        if album is () {
            http:Response notFound = new;
            notFound.statusCode = 404;
            return notFound;
        }
        return album;
    }

    // POST /albums/kind-of-blue — `album` is bound from the JSON body, `trace` from a header.
    resource function post [string id](Album album, @http:Header {name: "X-Trace-Id"} string? trace) returns Album {
        io:println("storing ", id, " (trace ", trace ?: "-", ")");
        albums[id] = album;
        return album;
    }
}
```

## Go Native Interpreter Support Status

This library is currently being migrated to Go to support the Ballerina Native Interpreter. The tables below outline the current support level for various features of this library in the Go implementation.

Support Levels:

- **Supported**: Fully implemented and tested in the Go version.
- **Partially Supported**: Implemented but lacking some edge cases, options, or sub-features. (See comments).
- **Not Yet Supported**: Planned for migration, but not yet implemented.
- **Cannot Support**: Cannot be implemented in the Go version due to technical limitations or architectural differences. (See comments).

### Client

| Feature/API | Support Status | Comments / Limitations |
|---|---|---|
| Core HTTP request methods | Supported | `get`, `post`, `put`, `patch`, `delete`, `head`, `options` are all implemented. |
| Custom HTTP verb execution | Supported | `execute` accepts any HTTP verb string. |
| Request forwarding via incoming request | Supported | `forward(path, request)` forwards the method, headers, and body of an `http:Request` to the upstream service; hop-by-hop headers are stripped per RFC 7230. |
| Request timeout | Supported | Configured via `timeout` in `ClientConfiguration` (decimal seconds, default 30). |
| HTTP version selection | Supported | `HTTP_1_0`, `HTTP_1_1`, and `HTTP_2_0` (default) are supported. Specifying `HTTP_1_0` at runtime prints a warning and falls back to HTTP/1.1, because Go's HTTP client cannot send HTTP/1.0 requests. |
| Redirect following | Supported | Full `FollowRedirects` record supported: `enabled`, `maxCount` (default 5), `allowAuthHeaders`. |
| Connection pooling | Supported | `PoolConfiguration` / `poolConfig` field in `ClientConfiguration`: `maxIdleConnections` (default 100), `maxActiveConnections` (-1 = unlimited), `waitTime` (default 30s). Defaults mirror jBallerina's pool config. |
| Custom request headers | Supported | Accepted as `map<string\|string[]>` on every method. When the message is an `http:Request`, its own headers are sent too: a `string` value in the `headers` argument replaces the request's header of the same name and a `string[]` value is appended to it, and `mediaType` overrides any `Content-Type`. `Connection`, `Keep-Alive`, `Proxy-Connection`, `Transfer-Encoding`, `Upgrade` and a `TE` other than a single `trailers` value are not sent. |
| Content-Type inference from payload type | Supported | `string` → `text/plain`, `xml` → `application/xml`, `byte[]` → `application/octet-stream`, all other `anydata` values → `application/json`. `RequestMessage` is `anydata\|Request\|mime:Entity[]`; a `mime:Entity[]` message, including an empty one, is sent as a multipart body with a generated boundary under `multipart/form-data`, and a part that cannot be encoded fails the call with an `error`. `stream<byte[], io:Error?>` messages are not supported. |
| Media type override | Supported | `mediaType` parameter on body-carrying methods overrides the inferred Content-Type. |
| TLS and mutual TLS (mTLS) | Partially Supported | PEM-file-based CA trust (`cert` as a string path) and client certificate/key pairs (`key` as `CertKey`) are supported. `crypto:TrustStore`, `crypto:KeyStore`, password-protected private keys (`keyPassword`), OCSP/CRL certificate revocation (`certValidation`), and TLS session timeout (`sessionTimeout`) are not supported. |
| Client-side response data binding | Partially Supported | Every remote and resource method except `head` takes a `TargetType targetType = <>` parameter inferred from the contextually expected type. An `http:Response` target (or any union containing it) yields the raw response; any other `anydata` target is deserialised from the body according to the `Content-Type` header. `stream<SseEvent, error?>` targets are not available, and jBallerina's `data.jsondata` projection options are not applied. An `application/xml` or `text/xml` body binds to an `xml` target, including a narrower one such as `xml:Element` when the parsed value inhabits it; an empty body for a non-nilable `xml` target returns an `http:NoContentError`, unlike the `string` and `byte[]` builders below. Conversion uses the same routine as `lang.value:fromJsonWithType`, so declared union member order is not honoured and record field defaults are not injected. An empty body binds to `()` for a nilable target; for a non-nilable `string` or `byte[]` target it binds to `""` or `[]` rather than raising jBallerina's `http:NoContentError`. A target narrower than the type its builder produces — an enum or a singleton for `text/plain`, a closed all-string record for `application/x-www-form-urlencoded`, a tuple or fixed-length array for `application/octet-stream` — is converted to that target, and a body that does not fit it returns an `error`. The nilable form of such a target (`Colour?`, `Form?`) binds the same way, with an absent body giving `()`; a narrow target that is not nilable instead receives the builder's empty value and rejects it unless the narrow type admits it. |
| Status code response binding | Not Yet Supported | `StatusCodeClient` and `getStatusCodeRecord()` are not implemented. |
| Status code error mapping | Partially Supported | When data binding is active, a 4xx or 5xx response yields an `error` whose message is the reason phrase and whose detail carries `statusCode`, `headers`, and `body`. The distinct types `http:ClientRequestError` and `http:RemoteServerError` are declared but not produced: the error carries only their type name, so the two cases cannot be distinguished with an `is` check until the client completion, and `error:detail()` is not available to read the detail. |
| Client authentication | Not Yet Supported | The `auth` field in `ClientConfiguration` is absent. BasicAuth (`CredentialsConfig`), BearerToken, self-signed JWT (`JwtIssuerConfig`), and all OAuth2 grant types are not supported. |
| Circuit breaker | Not Yet Supported | `circuitBreaker` configuration and `CircuitBreakerClient` are not implemented. |
| Automatic retry | Not Yet Supported | `retryConfig` configuration and `RetryClient` are not implemented. |
| Failover client | Not Yet Supported | `FailoverClient` is not implemented. |
| Load balancer client | Not Yet Supported | `LoadBalanceClient` is not implemented. |
| Cookie management | Not Yet Supported | `cookieConfig`, `CookieStore`, and `getCookieStore()` are not implemented. |
| HTTP response caching | Not Yet Supported | The `cache` (`CacheConfig`) configuration is not implemented. |
| Compression negotiation | Supported | `COMPRESSION_AUTO` adds no `Accept-Encoding` header (server decides). `COMPRESSION_ALWAYS` adds `Accept-Encoding: deflate, gzip` if not already set. `COMPRESSION_NEVER` removes any `Accept-Encoding` header. Compressed responses (`Content-Encoding: gzip` or `deflate`) are transparently decompressed in all modes; a `deflate` body may be a zlib stream, as RFC 9110 defines it, or a raw deflate stream, and the decoded response has no `Content-Encoding` or `Content-Length` header. |
| HTTP/1.x protocol settings | Not Yet Supported | `http1Settings` (keep-alive, chunking, proxy) is not implemented. |
| HTTP/2 protocol settings | Not Yet Supported | `http2Settings` (prior knowledge, initial window size) is not implemented. |
| Response size limits | Partially Supported | `responseLimits` (`ResponseLimitConfigs`) is implemented. `maxHeaderSize` maps to Go's `http.Transport.MaxResponseHeaderBytes`. `maxEntityBodySize` is enforced per-response via a counting reader (errors surface on payload extraction). `maxStatusLineLength` is accepted and validated (must be ≥ 0) but **not enforced at runtime** — Go's HTTP transport has no equivalent limit. |
| TCP socket configuration | Not Yet Supported | `socketConfig` (`ClientSocketConfig`) is not implemented. |
| Client-side payload validation | Not Yet Supported | The `validation` and `laxDataBinding` flags in `ClientConfiguration` are not implemented. |
| Proxy support | Supported | `ProxyConfig` is supported via the top-level `proxy` field in `ClientConfiguration`. Proxy auth (`userName`/`password`) is forwarded via HTTP CONNECT for HTTPS targets and `Proxy-Authorization` for HTTP targets. The deprecated `http1Settings.proxy` path is not supported (we have no `http1Settings`). DNS resolution of the proxy hostname is lazy (per-request) rather than eager at client init — initialization does not fail on an unresolvable proxy host. |
| Async request submission | Not Yet Supported | `submit`, `getResponse`, and `HttpFuture` are not implemented. |
| HTTP/2 server push | Not Yet Supported | `hasPromise`, `getNextPromise`, `getPromisedResponse`, and `rejectPromise` are not implemented. |
| Resource function call syntax | Partially Supported | All seven accessors (`get`, `post`, `put`, `patch`, `delete`, `head`, `options`) are callable with the client resource access syntax — `client->/albums/[id].get(...)`, with `get` implied when no accessor is named. Path segments are typed `PathParamType` (`boolean\|int\|float\|decimal\|string`) values, and query parameters are passed as named arguments collected by the `*QueryParams` included record parameter. Every accessor except `head` takes a `TargetType targetType = <>` parameter and binds the payload exactly as the remote methods do (see *Client-side response data binding*). The `@http:Query` annotation for overriding a query parameter's name on the wire is not supported, and neither are rest-spread path segments (`client->/p/[...segs]`), which fail to compile. |

### Request

| Feature/API | Support Status | Comments / Limitations |
|---|---|---|
| Request object construction | Supported | `new http:Request()` creates an outbound request with `rawPath`, `method`, and `httpVersion` fields. |
| Request write methods | Supported | `setTextPayload`, `setJsonPayload`, `setXmlPayload`, `setBinaryPayload` (each with optional `contentType`), `setHeader`, `addHeader`, `removeHeader`, `removeAllHeaders`, and `setContentType` populate the request. All four payload setters follow jBallerina's rule of keeping an existing `Content-Type` when no override is passed, falling back to their type-specific default only when none is set. |
| Request read methods | Supported | `getTextPayload`, `getJsonPayload`, `getXmlPayload`, `getBinaryPayload`, `getHeader`, `getHeaders`, `hasHeader`, `getHeaderNames`, `getContentType`, `getQueryParams`, `getQueryParamValue`, and `getQueryParamValues` read from client-constructed or inbound requests. The payload accessors return `http:ClientError`: `getTextPayload`, `getJsonPayload` and `getXmlPayload` return `http:NoContentError` (`No content`) when the request has no payload, or when a `json` payload is empty (`getBinaryPayload` returns an empty `byte[]`), and `http:GenericClientError` (`Error occurred while retrieving the <kind> payload from the request`) when the body cannot be read or decoded. A payload explicitly set to an empty string reads back as `""` from `getTextPayload` and as empty `xml` from `getXmlPayload`. `getHeader` and `getHeaders` return `http:HeaderNotFoundError` (`Http header does not exist`) for a missing header. |
| Generic payload setter | Partially Supported | `setPayload(json\|xml\|byte[]\|mime:Entity[] payload, string? contentType = ())` dispatches by runtime type to `setTextPayload`/`setXmlPayload`/`setBinaryPayload`/`setJsonPayload`/`setBodyParts`. jBallerina's signature also accepts `stream<byte[], io:Error?>`/`stream<SseEvent, error?>`, not accepted here since `http` doesn't support those payload kinds yet; `anydata` values outside `json` and `xml` (e.g. `table`) are also not accepted, since this port has no `toJson()` conversion for them. |
| Form-urlencoded payload parsing | Supported | `getFormParams()` decodes an `application/x-www-form-urlencoded` body into a `map<string>`. Returns an `http:GenericClientError` (`Error occurred while retrieving form parameters from the request`) if the `Content-Type` header is missing, invalid, or not `application/x-www-form-urlencoded`, and an `http:ClientError` if the body cannot be decoded. |
| Multipart and form-data payload | Partially Supported | `setBodyParts(mime:Entity[] bodyParts, string? contentType = ())` / `getBodyParts() returns mime:Entity[]\|http:ClientError`, built on `ballerina/mime`'s multipart support. As in jBallerina, `getBodyParts()` returns the parts given to `setBodyParts` as-is and keeps the parts it decodes from a body (so edits to them are seen by a later call and sent by `forward`), the parts are serialized only when the request is sent (so later edits to a part are sent, and a boundary in the final Content-Type, including one from a `mediaType` argument or `Content-Type` header, is used), and `getContentType()` reports the Content-Type as set: an explicit boundary given through `contentType` or an existing `Content-Type` header is kept, while a generated boundary is added to the Content-Type sent on the wire and, as in jBallerina, written back to the Request's Content-Type once a client call or `forward` sends it. Parts sent with no Content-Type go out as `multipart/form-data` with the generated boundary; jBallerina sends no usable body in that case. A `getBodyParts()` failure returns an `http:GenericClientError` (`Error occurred while retrieving body parts from the request`) with the underlying `mime` error as its cause. Unlike jBallerina, which sends a part with an unsupported charset as-is, such a part makes the client call return `failed to encode multipart body: <charset>`. A part whose own body is `mime:Entity[]` is encoded recursively as a nested multipart body, while decoding an inbound body is flat (single-level) only, matching `mime`'s own limitation. `RequestMessage` (accepted by the client's `post`/`put`/`patch`/`delete`/`execute` methods) is widened to include `mime:Entity[]`. |
| Path parameter binding | Supported | Path segments are coerced to the declared `string`, `int`, `float`, `decimal`, or `boolean` path parameter types, including rest path parameters. |
| Query parameter binding | Partially Supported | Unannotated parameters and `@http:Query` parameters of type `string`, `int`, `float`, `decimal`, `boolean`, `map<anydata>`/records (sent as JSON), arrays of these, and their nilable forms bind from the query string, following jBallerina's parser: values are split on commas, keys are not URL-decoded, and the first value binds to a non-array parameter. A value-less parameter binds to `()` when nilable, and so does a missing one unless the service sets `treatNilableAsOptional: false`; otherwise the request yields 400. A defaultable parameter (`int id = 10`) does not receive its default when the query parameter is absent; it yields 400 instead, because the runtime does not expose parameter defaults to native code. |
| Inbound header binding | Partially Supported | `@http:Header` parameters of type `string`, `int`, `float`, `decimal`, `boolean`, arrays of these, nilable forms, and closed records of these bind from request headers; `@http:Header {name}` renames the header. An empty header binds to `()` when nilable, and so does an absent one unless the service sets `treatNilableAsOptional: false`; otherwise the request yields 400, except that a nilable header record parameter binds `()` when one of its headers is absent. On a header record, a field-level `@http:Header {name}` is ignored and the field name is used as the header name, because record field annotations are not reachable from a parameter type. An `http:Headers` parameter gives read access to all request headers (`hasHeader`, `getHeader`, `getHeaders`, `getHeaderNames`); its `getHeader` and `getHeaders` return `error` rather than the distinct `HeaderNotFoundError`, which is not declared. |
| Inbound payload binding | Partially Supported | `@http:Payload` parameters, and the default payload parameter (the single unannotated structured or `xml` parameter of a non-`get`/`head`/`options` resource), are bound from the body using the builder the `Content-Type` selects, falling back to the parameter type when it is absent or unknown. An empty body binds to `()` for a nilable type; binding failures yield 400 with a `data binding failed: ...` message. A union type is matched by preferring `string` over `byte[]` over a form `map<string>`, rather than in declared member order. With `laxDataBinding` set on the service, a JSON body bound to a record, but not a nilable record or a map, is projected as jBallerina's lax binding does: a field a closed record lacks is dropped, a `null` on an optional field that does not admit `()` removes the field, and an absent required nilable field becomes `()`, in records nested in fields, maps and arrays too. A record with only a rest field, such as `record {\| T...; \|}`, is the same type as `map<T>` and is bound strictly like a map, where jBallerina projects it as a record. A `mediaType` on `@http:Payload` is accepted but not enforced, as in jBallerina. A `Request` parameter declared alongside a payload parameter can still read the body. On a resource return type, `@http:Payload {mediaType}` is accepted but has no effect; the response Content-Type is still inferred from the returned value. |
| Streaming request body | Not Yet Supported | `stream<byte[], io:Error?>` as a request payload type is not implemented. |

### Response

| Feature/API | Support Status | Comments / Limitations |
|---|---|---|
| Response status code access | Supported | Exposed as the `statusCode` field on `Response`. |
| Response payload as text | Supported | `getTextPayload()` returns `string\|http:ClientError`: `http:NoContentError` (`No content`) when the response has no payload, and `http:GenericClientError` when the body cannot be read. |
| Response payload as JSON | Supported | `getJsonPayload()` parses the body and returns `json\|http:ClientError`: `http:NoContentError` (`No content`) for an empty body, and `http:GenericClientError` (`Error occurred while retrieving the json payload from the response`) for a body that is not valid JSON. |
| Response payload as XML | Supported | `getXmlPayload()` parses the body and returns `xml\|http:ClientError`: `http:NoContentError` (`No content`) when the response has no payload, and `http:GenericClientError` (`Error occurred while retrieving the xml payload from the response`) for malformed XML. A payload explicitly set to an empty string reads back as empty `xml`. |
| Response payload as raw bytes | Supported | `getBinaryPayload()` returns `byte[]\|http:ClientError`. A response without a payload returns an empty `byte[]`. |
| Response header inspection | Supported | `hasHeader`, `getHeader`, `getHeaders`, and `getHeaderNames` operate on transport (leading) headers. Trailing header position is accepted at compile time but has no runtime effect. `getHeader` and `getHeaders` return `http:HeaderNotFoundError` (`Http header does not exist`) for a missing header. |
| Response object construction | Supported | `new http:Response()` creates a response with status code 200; initialised via `init()`. |
| Response write methods | Supported | `setTextPayload`, `setJsonPayload`, `setXmlPayload`, `setBinaryPayload` (each with optional `contentType`), `setHeader`, `addHeader`, `removeHeader`, `removeAllHeaders`, and `setContentType` populate a constructed `Response`. All four payload setters follow jBallerina's rule of keeping an existing `Content-Type` when no override is passed, falling back to their type-specific default only when none is set. Status code is set by direct field assignment (`resp.statusCode = 404`). |
| Generic payload setter | Partially Supported | `setPayload(json\|xml\|byte[]\|mime:Entity[] payload, string? contentType = ())` dispatches by runtime type to `setTextPayload`/`setXmlPayload`/`setBinaryPayload`/`setJsonPayload`/`setBodyParts`. jBallerina's signature also accepts `stream<byte[], io:Error?>`/`stream<SseEvent, error?>`, not accepted here since `http` doesn't support those payload kinds yet; `anydata` values outside `json` and `xml` (e.g. `table`) are also not accepted, since this port has no `toJson()` conversion for them. |
| Multipart and form-data payload | Partially Supported | `setBodyParts(mime:Entity[] bodyParts, string? contentType = ())` / `getBodyParts() returns mime:Entity[]\|http:ClientError`, built on `ballerina/mime`'s multipart support. As in jBallerina, `getBodyParts()` returns the parts given to `setBodyParts` as-is and keeps the parts it decodes from a body (so edits to them are seen by a later call), the parts are serialized only when the response is written (so later edits to a part, or a boundary set later through the Content-Type header, are honoured), and `getContentType()` reports the Content-Type as set: an explicit boundary given through `contentType` or an existing `Content-Type` header is kept, while a generated boundary is added only to the Content-Type sent on the wire. A response holding parts but no Content-Type is written as `multipart/form-data` with the generated boundary; jBallerina sends no usable body in that case. A `Content-Length` copied from a backend response is dropped once its parts are re-encoded. A `getBodyParts()` failure returns `Error occurred while retrieving body parts from the response: <mime error>`, with the `mime` error also as its cause. Unlike jBallerina, which writes a part with an unsupported charset as-is, a listener returning such a response sends a 500 with `failed to encode multipart body: <charset>`. A part whose own body is `mime:Entity[]` is encoded recursively as a nested multipart body, while decoding an inbound body is flat (single-level) only, matching `mime`'s own limitation. |
| Streaming response body | Not Yet Supported | `getByteStream()` is not implemented. |
| Server-Sent Events | Not Yet Supported | `getSseEventStream()` and consuming a `stream<SseEvent, error?>` response are not implemented. |

### Listener

| Feature/API | Support Status | Comments / Limitations |
|---|---|---|
| HTTP Listener | Supported | The `Listener` class is implemented: `init`, `attach`, `detach`, `'start`, `gracefulStop`, and `immediateStop` create a listener, attach/detach services, and start/stop the server. See the `gracefulStop` behavioural note below. |

### Service

| Feature/API | Support Status | Comments / Limitations |
|---|---|---|
| HTTP service definition and routing | Supported | Path-based routing dispatches to the first attached service whose base path matches, not longest-prefix match; attach overlapping base paths on the same listener in most-specific-first order. |
| Resource function dispatch | Partially Supported | Path parameters (typed segment coercion) and accessor methods (`get`, `post`, `put`, `patch`, `delete`, `head`, `options`, `default`) dispatch to the matching resource function, which may declare an `http:Request` parameter, an `http:Caller` parameter, and query, header, and payload parameters (see the Request table). Resource return values may be `http:Response`, a status code response record, `error`, `()`, or any `anydata` value; an `anydata` return is serialised with the Content-Type its type implies and answered with 201 for a `post` accessor and 200 otherwise, `()` gives 202, and an `error` is sent as described in *Error responses from resources*. Status code response records are covered in the row below. An `OPTIONS` request that no `options` or `default` resource serves is answered with 204 and an `Allow` header listing the methods the path serves, followed by `OPTIONS`, or every method of the service at its base path (written as declared, with any trailing slashes, and without a query); a path no resource serves answers 404, and a CORS preflight is answered as *CORS configuration* describes. jBallerina lists the methods in declaration order, which the runtime does not expose, so they are listed as `GET, HEAD, POST, DELETE, PATCH, PUT`, then any custom methods sorted. |
| Caller-based response dispatch | Partially Supported | A resource can declare one `http:Caller` parameter. `respond` sends an `http:Response`, a status code response record, an `error` (sent as a returned error is, after mapping an `http:ClientConnectorError` to `httpscerr:BadGatewayError`), `string`, `xml`, `byte[]`, `mime:Entity[]` or any other `anydata` value as JSON, with 201 for a `post` resource's payload. Only the first `respond` is sent; a later one returns `http:GenericListenerError` (`illegal respond: response has already been sent`), as does one made after the resource has returned. A resource that returns without responding answers 500 with no body, or its returned error's response; one that returns an error after responding has the error ignored and prints `illegal return: response has already been sent` to stderr. `redirect` (an empty `locations` array sends an empty `Location` header), `'continue`, `getRemoteHostName` and the `remoteAddress`, `localAddress` and `protocol` fields (`"http"`, also over TLS, as in jBallerina) are supported. `respond` returns an `http:GenericListenerError` when the response cannot be sent as given (for example an informational status such as 103) and a 500 goes out instead. A `Caller` resource runs on until it returns after responding; the response is complete as soon as `respond` sends it. A resource that panics before responding, with or without a `Caller`, gets a 500 with the panic message as `text/plain`, as in jBallerina; a panic after responding is logged to stderr and sends nothing more; addresses are written the way Java writes them (`0:0:0:0:0:0:0:1` for `::1`). The compiler plugin rejects a second `http:Caller` parameter and a `Caller` resource whose return type allows anything other than `error` or nil. Not yet supported: the `@http:CallerInfo` annotation (`http:HttpCallerInfo`) and the compiler plugin check of `respond` arguments against its `respondType`; the `stream` members of `http:ResponseMessage`; sending the same `http:Response` twice is not detected; a failed write is not reported by `respond`. With `Expect: 100-continue`, the 100 is sent when the request body is first read, which for a body of up to 8 KiB or one bound to a payload parameter is before the resource runs, so `'continue()` does not control it. |
| HTTP/2 server push from a service | Not Yet Supported | `http:PushPromise`, `Caller.promise` and `Caller.pushPromisedResponse` are not declared. |
| Status code response types from resources | Partially Supported | All 61 `StatusCodeResponse` record types (`http:Ok`, `http:Created`, `http:NotFound`, ...), `http:DefaultStatusCodeResponse`, their `Status` classes, and the `STATUS_*` status code constants are declared. A returned record is sent with its `status.code`, its `headers` (a `string[]`, `int[]` or `boolean[]` value adds one header per element), and its `body`: `xml`, `string` and `byte[]` set the matching payload, an `application/x-www-form-urlencoded` `mediaType`, matched ignoring case and parameters, url-encodes a `map<string>` body, and any other `anydata` body is sent as JSON, with members in their source order and nested `xml` written as its string form. The `mediaType` field, trimmed, overrides a `Content-Type` given in `headers`, which in turn overrides the payload's default. A record type that includes a status code record (`record {\| *http:Ok; Album body; \|}`) is sent the same way. Not yet supported: the `readonly &` response constants such as `http:OK` and `http:NOT_FOUND` ([#1654](https://github.com/ballerina-nutcracker/ballerina/issues/1654), [#1043](https://github.com/ballerina-nutcracker/ballerina/issues/1043)); the `@http:Payload` return media type ([#1409](https://github.com/ballerina-nutcracker/ballerina/issues/1409)); `@http:Header` renaming of `headers` record fields; and the `@deprecated` annotation on `http:NetworkAuthorizationRequired` ([#1291](https://github.com/ballerina-nutcracker/ballerina/issues/1291)). A body that cannot be encoded for its media type, including a `NaN` or infinite `float` in a JSON body, gives a 500, and so does a status that cannot end a response: a code outside 100–999, or an informational 1xx other than 101 (`http:Continue`, `http:Processing`, `http:EarlyHints`). Until [#1076](https://github.com/ballerina-nutcracker/ballerina/issues/1076) and [#1043](https://github.com/ballerina-nutcracker/ballerina/issues/1043) are fixed, each `Status<Name>` class declares an empty `isolated function init()` and each record creates its own status object rather than sharing a module-level one, which callers can observe only through `===`. |
| Error responses from resources | Partially Supported | A returned `error` is sent the way jBallerina's default error interceptor sends it. An `http:ApplicationResponseError` (`http:ClientRequestError`, `http:RemoteServerError`) is sent with the `statusCode`, `headers` and `body` of its detail. For any other error, the status comes from its `http.httpscerr` type (`httpscerr:NotFoundError` gives 404, and so on); an `httpscerr:DefaultStatusCodeError` uses its `statusCode` detail, or else its cause's status; any other error gives 500. For an `httpscerr` error, a `body` in the detail is sent as a status code response body would be, and its `headers` are added with or without a `body`; with no `body`, and for any other error (whose detail is ignored), the body is an `http:ErrorPayload` JSON (`timestamp`, `status`, `reason`, `message`, `path` with the query string, `method`) whose `reason` is jBallerina's reason phrase (for example `Request-URI Too Long` for 414, `Client Error (418)` for 418). Every returned error is logged as `unhandled error returned from the service`. Requests no resource matches answer 404 (`no matching service found for path: <path>` or `no matching resource found for path : <path> , method : <method>`) and 405 (`Method not allowed`) with the same payload. A status that cannot end a response gives a 500, as for status code records. Not yet supported: jBallerina's client calls return an `http:ApplicationResponseError` for a 4xx or 5xx response, so a resource that passes it on answers with the upstream status and body; this port's client does not return that error type yet ([#810](https://github.com/ballerina-nutcracker/ballerina/issues/810)), so the passed-on error gives 500. |
| Service-level annotation | Partially Supported | `@http:ServiceConfig` is declared with jBallerina's fields except `auth`, which waits for listener authentication, and `serviceType`, which needs `ServiceContract` ([#1294](https://github.com/ballerina-nutcracker/ballerina/issues/1294)). `host`, `treatNilableAsOptional`, `laxDataBinding`, `mediaTypeSubtypePrefix`, `compression`, `chunking` and `cors` are honoured. Services with a `host` answer the requests whose `Host` header names that host, those for the exact host and port taking precedence over those for the host name, and the services without one answer the rest, so two services may share a base path on different hosts. The prefix is added to the subtype of every `Content-Type` a resource of the service sends, including its binding and error responses (`application/vnd.x+json`), but not to the 404 and 405 sent when no resource matches. `validation` ([#1353](https://github.com/ballerina-nutcracker/ballerina/issues/1353)) and `openApiDefinition` are accepted but have no effect yet. As in jBallerina, the compiler rejects a `mediaTypeSubtypePrefix` literal that is not a valid subtype or has a `+` suffix, and a `basePath` on a service declaration. |
| Resource-level annotation | Not Yet Supported | `@http:ResourceConfig` and `HttpResourceConfig` are declared without the `auth` field, so annotated resources compile, but the annotation has no effect: method annotations cannot be read at runtime ([#1361](https://github.com/ballerina-nutcracker/ballerina/issues/1361)). |
| Response cache annotation | Not Yet Supported | `@http:Cache` on resource return types is not implemented. |
| CORS configuration | Partially Supported | The `cors` of `@http:ServiceConfig` applies to every resource of the service, as jBallerina's `CorsHeaderGenerator` does. A response to a request whose `Origin` values are all allowed gets `Access-Control-Allow-Origin` (the request's origins, also when `*` is allowed), and `Access-Control-Allow-Credentials` and `Access-Control-Expose-Headers` when configured, replacing any the resource set; the dispatcher's 404 and 405 get none. An `OPTIONS` request that no resource serves is a preflight when it has one origin and one `Access-Control-Request-Method` that the path serves and the config allows, along with its request headers: it gets 204 with `Access-Control-Allow-Origin` and `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers` when the request lists headers, and `Access-Control-Allow-Credentials` and `Access-Control-Max-Age` when configured; otherwise it gets the `Allow` response. As in jBallerina, a preflight for `HEAD` is accepted on a path with a `get` resource, although the `HEAD` request itself gets 405. A config with any field set allows every origin and method it does not list. Not yet supported: the `cors` of `@http:ResourceConfig`, because method annotations cannot be read at runtime ([#1361](https://github.com/ballerina-nutcracker/ballerina/issues/1361)). |
| Request interceptors | Partially Supported | A service of type `http:InterceptableService` engages the `http:RequestInterceptor` services its `createInterceptors` method returns, which is called when the listener starts, or on attach to a started listener. The interceptors whose resource matches the request path and method run in order, before the resource of the service is matched, so its 404 or 405 comes after them; an interceptor whose resource does not match is skipped. Interceptor resources bind parameters as service resources do, and the headers, payload and body parts an interceptor sets on its `http:Request` reach the stages after it. The request body of such a service is read in full before the first interceptor runs, so with `Expect: 100-continue` the 100 is sent then. `ctx.next()` returns the next interceptor, then the service, and each call advances; returning the stage it reached continues the request, while returning another service answers 500 with an `http:InterceptorReturnError`. Returning `()` answers 202, or 500 from an interceptor with an `http:Caller` parameter that sent no response, and any other value, `http:Response`, status code response or error is the response, with the `@http:ServiceConfig` of the service applied. A panic answers 500, as in a service resource. The compiler plugin checks interceptor classes as jBallerina's does (one interceptor type, one resource method, no remote method, no resource annotation, the return type). Not yet supported: the `error` parameter, the `JWT_INFORMATION` member, which needs `ballerina/jwt`, and streaming the request body of such a service, which is held in memory so that each stage can read it. |
| Response and error interceptors | Not Yet Supported | `http:ResponseInterceptor`, `http:RequestErrorInterceptor` and `http:ResponseErrorInterceptor` are declared, but a listener with a service that engages one fails to start, and attach fails, with `interceptor service registration failed: response and error interceptors are not yet supported`. Errors are sent the way jBallerina's default error interceptor sends them. |
| Request context | Partially Supported | `http:RequestContext` (`set`, `get`, `hasKey`, `keys`, `remove`, `getWithType` and `next`) is shared by the interceptors and the service resource of a request, and a resource of any service may declare it; `next` on a context the dispatcher did not create returns an `http:InterceptorReturnError`. `http:Cloneable` lacks its `table<map<Cloneable>>` member, since table types are not yet supported ([#294](https://github.com/ballerina-nutcracker/ballerina/issues/294)), and the cause of a `getWithType` error uses the runtime's wording. |
| Service contract type | Not Yet Supported | `ServiceContract` type for contract-first service definitions is not implemented. |
| Service-level compression and chunking | Supported | As in jBallerina, every response, including the dispatcher's 404 and 405, is compressed with gzip or deflate when the request's `Accept-Encoding` asks for it (`COMPRESSION_AUTO`, the default); `COMPRESSION_ALWAYS` also uses gzip when the request has no `Accept-Encoding` or only `identity`, `COMPRESSION_NEVER` turns compression off, and a non-empty `contentTypes` limits it to responses whose `Content-Type` contains one of them. A `Content-Encoding: gzip` or `deflate` set by the resource compresses the body with that coding, and `identity` sends it as is. Responses without a body (`HEAD`, 204, 304) and empty bodies are not compressed. Over HTTP/1.1, `CHUNKING_AUTO` sends a body over 8192 bytes chunked and a smaller one with a `Content-Length`, `CHUNKING_ALWAYS` always chunks and `CHUNKING_NEVER` never does, holding a streamed body in memory to measure it unless the response already has a `Content-Length`; an HTTP/1.0 request always gets a `Content-Length`, and HTTP/2 has no chunking. The compressed bytes are Go's `compress/gzip` and `compress/zlib` output, so their size differs from Netty's. |
| Inbound payload validation | Not Yet Supported | Automatic constraint validation of inbound request payloads via `ballerina/constraint` is not implemented. |

|---|---|---|
| Header value parsing utility | Partially Supported | `parseHeader()` parses comma-separated header values with parameters into `HeaderValue[]`, and returns an `http:GenericClientError` (`failed to parse: ...`) for a segment with parameters but no value. Unlike jBallerina, it rejects empty segments and maps a parameter without `=` to `""` ([#1734](https://github.com/ballerina-nutcracker/ballerina/issues/1734)). |
| HTTP version enum | Supported | `HttpVersion` with `HTTP_1_0`, `HTTP_1_1`, and `HTTP_2_0` enum constants. `HTTP_1_0` prints a runtime warning and falls back to HTTP/1.1. |
| Distinct HTTP error types | Partially Supported | The full `http:Error` hierarchy and the `http.httpscerr` status code errors are declared. `Request` and `Response` payload, header, form and body part accessors, `parseHeader`, and `Listener` initialisation return the jBallerina error types (`http:ClientError`, `http:NoContentError`, `http:HeaderNotFoundError`, `http:ListenerError`). The `Listener` lifecycle methods are declared `error?`, as in jBallerina, and their failures are `http:GenericListenerError` values. The `Client` remote and resource methods still return plain `error` values, so `http:ClientRequestError`, `http:RemoteServerError` and the other client error subtypes are never produced. The 14 types jBallerina declares as `distinct` over an intersection (for example `QueryParameterBindingError`, `ApplicationResponseError`, `httpscerr:DefaultStatusCodeError`) are declared as a module-private `distinct` base intersected with the remaining types until the interpreter supports that form ([#617](https://github.com/ballerina-nutcracker/ballerina/issues/617), [#1427](https://github.com/ballerina-nutcracker/ballerina/issues/1427)); they admit the same errors and the same type tests succeed. |
| Observability and metrics | Not Yet Supported | Metrics and tracing integration via `ballerina/observe` is not implemented. |
| XML payloads | Partially Supported | `setXmlPayload()` and `getXmlPayload()` are declared on both `Request` and `Response`, `RequestMessage` admits `xml` (an `xml` message is sent as `application/xml`), `application/xml` and `text/xml` responses bind to `xml` targets, and a resource may return `xml`. Multipart XML parts use `mime:Entity`'s own `setXml`/`getXml`, and `setPayload` accepts `xml`. A body of plain text that is not an XML document is decoded as an `xml` text item instead of failing as in jBallerina ([#1735](https://github.com/ballerina-nutcracker/ballerina/issues/1735)). |

### Notable Behavioural Changes

- **Transport-owned request headers are not sent.** jBallerina sends the `Upgrade`, `Keep-Alive`, `Proxy-Connection`, `Transfer-Encoding` and `TE` headers of an outbound request, such as an inbound `http:Request` passed through to a client, and replaces `Connection` with its own value; the Go-native version drops these, except a single `TE: trailers` header, because Go's transport sets them and its HTTP/2 transport rejects a request that carries them.
- **The status line carries Go's reason phrase.** jBallerina writes Netty's reason phrase on the HTTP status line, for example `HTTP/1.1 418 Client Error (418)` or `HTTP/1.1 414 Request-URI Too Long`; the Go-native version writes the phrase Go's `net/http` server uses (`418 I'm a teapot`, `414 URI Too Long`), since it does not allow a custom one. The `reason` in an `http:ErrorPayload` body is jBallerina's, and Ballerina clients see only the status code.
- **A status that cannot end a response gives a 500.** jBallerina sends a returned `http:Continue`, `http:Processing` or `http:EarlyHints` as an interim response and never completes it, so the client waits until it times out, and writes a malformed status line for a `DefaultStatus` code outside 100–999; the Go-native version answers 500 (`invalid status code for a response: <code>`) for a code outside 100–999 or an informational 1xx other than 101, whether it comes from a status code record, an `http:Response` or a returned error's status (a returned error's `body` and `headers` are then dropped) (<https://github.com/ballerina-platform/ballerina-library/issues/9812>, <https://github.com/ballerina-platform/ballerina-library/issues/9813>).
- **A `NaN` or infinite float in a JSON body gives a 500.** jBallerina writes it as a bare `NaN` token, sending an `application/json` body that is not JSON; the Go-native version fails the body's JSON conversion, so a resource returning it answers 500 and `setJsonPayload` panics (<https://github.com/ballerina-platform/ballerina-library/issues/9814>).
- **A form `mediaType` is matched ignoring case and parameters.** jBallerina url-encodes a status code record's `body` only for the exact `mediaType` `application/x-www-form-urlencoded`, so `Application/X-WWW-Form-Urlencoded` or `application/x-www-form-urlencoded; charset=UTF-8` sends the body as JSON under a form Content-Type; the Go-native version url-encodes it for any spelling of that media type (<https://github.com/ballerina-platform/ballerina-library/issues/9911>).
- **JSON bodies are written without spaces.** jBallerina writes a JSON body with its `toString` form, which puts a space after each `,` between members (`{"title":"Blue Train", "year":1957}`); the Go-native version writes compact JSON (`{"title":"Blue Train","year":1957}`) for `setJsonPayload`, `anydata` resource returns, status code response bodies, and `http:ErrorPayload` error bodies. Both are the same JSON value. A record's fields are written in the order the value was constructed rather than jBallerina's declaration order ([#1381](https://github.com/ballerina-nutcracker/ballerina/issues/1381)).
- **'continue() returns without an Expect header.** jBallerina's `Caller->'continue()` never returns when the request has no `Expect: 100-continue` header, so the resource never responds and the client gets no response; the Go-native version sends the interim `100 Continue` and returns, and the resource's `respond` then completes the request (<https://github.com/ballerina-platform/ballerina-library/issues/9852>).
- **Service host matching ignores the port and letter case.** jBallerina compares `@http:ServiceConfig {host}` with the whole `Host` header, so `host: "localhost"` never matches a request to `localhost:9090` and `Host: LOCALHOST:9090` does not match `host: "localhost:9090"`; the Go-native version compares host names case-insensitively, and a configured host without a port matches any port (<https://github.com/ballerina-platform/ballerina-library/issues/9867>).
- **The media-type subtype prefix is added once and not to multipart types.** jBallerina adds a service's `mediaTypeSubtypePrefix` to every response `Content-Type`, so `application/vnd.test+json` is sent as `application/vnd.test+vnd.test+json` and a multipart body as `multipart/vnd.test+form-data`, which clients no longer read as multipart; the Go-native version leaves a `Content-Type` unchanged when its subtype already starts with the prefix or its type is `multipart` (<https://github.com/ballerina-platform/ballerina-library/issues/9868>).
- **A Content-Encoding the listener cannot apply is kept.** Over HTTP/1.1, jBallerina removes a `Content-Encoding` the resource set that it cannot apply, such as `br`, and sends the body unchanged, so a body the resource encoded itself arrives unlabelled; the Go-native version keeps the header and the body (<https://github.com/ballerina-platform/ballerina-library/issues/633>).
- **HTTP/2 responses get the same Content-Encoding as HTTP/1.1.** Over HTTP/2, jBallerina sends `content-encoding: identity` for a response it does not compress, sends a `Content-Encoding` on 204, 304 and `HEAD` responses, and compresses an empty body; the Go-native version sends no `Content-Encoding` in these cases, as jBallerina does over HTTP/1.1 (<https://github.com/ballerina-platform/ballerina-library/issues/9878>).
- **Accept-Encoding codings match case-insensitively.** jBallerina matches `Accept-Encoding` codings case-sensitively, so `GZIP` gets an uncompressed response and, under `COMPRESSION_ALWAYS`, `Identity` or `identity;q=1` is not treated as `identity`; the Go-native version matches them case-insensitively, as RFC 9110 requires (<https://github.com/ballerina-platform/ballerina-library/issues/9880>).
- **Accept-Encoding: * is answered with gzip.** Over HTTP/1.1, jBallerina answers `Accept-Encoding: *` with a `snappy` body, which is not a registered HTTP content coding; the Go-native version uses gzip, as jBallerina does over HTTP/2 (<https://github.com/ballerina-platform/ballerina-library/issues/9879>).
- **Negotiated responses carry Vary: Accept-Encoding.** jBallerina picks a response's content coding from `Accept-Encoding` without `Vary: Accept-Encoding`, so a shared cache can serve a gzip response to a client that cannot decode it; the Go-native version adds `Accept-Encoding` to `Vary` whenever the service's compression config lets `Accept-Encoding` choose the coding, that is unless compression is `COMPRESSION_NEVER`, the resource set a `Content-Encoding`, or the content type is outside `contentTypes` (<https://github.com/ballerina-platform/ballerina-library/issues/9898>).
- **A rest path parameter matches no segments.** jBallerina does not select `post files/[string... path]` for `POST /files`, answering 404 or 405, and leaves its method out of the `Allow` header and CORS preflight for `/files`; the Go-native version binds `path` to `[]`, lists the method and accepts the preflight (<https://github.com/ballerina-platform/ballerina-library/issues/9560>, <https://github.com/ballerina-platform/ballerina-library/issues/9655>).
- **CORS responses carry Vary: Origin.** jBallerina echoes the request's origin in `Access-Control-Allow-Origin` without `Vary: Origin`, so a shared cache can serve one origin's response to another; the Go-native version adds `Vary: Origin` to every resource response of a service with a CORS config, including one to a request without an `Origin`, as the Fetch standard's CORS and HTTP caches section asks (<https://github.com/ballerina-platform/ballerina-library/issues/9564>).
- **Credentials are allowed only for listed origins.** jBallerina answers any origin with `Access-Control-Allow-Credentials: true` when `allowCredentials` is set without `allowOrigins`, letting every site make credentialed requests; the Go-native version sends `Access-Control-Allow-Credentials` only when `allowOrigins` lists the origins (<https://github.com/ballerina-platform/ballerina-library/issues/9882>).
- **A resource's Allow header is kept.** jBallerina removes the `Allow` header from every resource response it adds CORS headers to, including a 405 the resource returns; the Go-native version keeps it and leaves `Allow` out only of preflight responses (<https://github.com/ballerina-platform/ballerina-library/issues/9883>).
- **Preflight request headers may have spaces after commas.** jBallerina splits `Access-Control-Request-Headers` on commas without trimming, so `X-A, X-C` fails the preflight while `X-A,X-C` passes; the Go-native version trims each name (<https://github.com/ballerina-platform/ballerina-library/issues/9566>).
- **Access-Control-Max-Age is sent only when maxAge is set.** jBallerina sends `Access-Control-Max-Age: -1` on a preflight response when `maxAge` is not configured; the Go-native version leaves the header out (<https://github.com/ballerina-platform/ballerina-library/issues/9565>).
- **Responses from request interceptors follow the service configuration.** jBallerina sends a response from a request interceptor without the CORS headers and the media-type subtype prefix of its service's `@http:ServiceConfig`; the Go-native version applies them, as to the service's own responses (<https://github.com/ballerina-platform/ballerina-library/issues/9887>).
- **A request interceptor that returns `()` ends the request.** jBallerina answers 202 for `()` returned after `ctx.next()` and still runs the next stage, whose response is then rejected; the Go-native version answers 202 and runs nothing more (<https://github.com/ballerina-platform/ballerina-library/issues/9884>).
- **A binding failure in a request interceptor is answered.** jBallerina logs a parameter of an interceptor resource it cannot bind and never answers the request; the Go-native version answers with the binding error, as for a service resource, for example 400 for a missing query parameter (<https://github.com/ballerina-platform/ballerina-library/issues/9885>).
- **Request interceptors leave OPTIONS requests to the service.** jBallerina answers an OPTIONS request with the `Allow` header of a request interceptor whose resource serves another method, and fails a CORS preflight with a `ClassCastException`; the Go-native version skips such an interceptor, so the service answers both (<https://github.com/ballerina-platform/ballerina-library/issues/9886>).
- **A service attached to a started listener gets its interceptors.** jBallerina calls `createInterceptors` only when the listener starts, so a service attached afterwards runs without its interceptors; the Go-native version calls it on attach (<https://github.com/ballerina-platform/ballerina-library/issues/9585>).
- **getWithType returns a copy of the member.** jBallerina's `RequestContext.getWithType` returns the stored member itself, so changing a list or map it returns changes the member without `set`; the Go-native version returns a copy, as `get` does, since it reads the member under the lock of the isolated `RequestContext` (<https://github.com/ballerina-platform/ballerina-library/issues/9915>).
- **redirect with no locations sends an empty Location header.** jBallerina's `Caller->redirect` panics with `invalid substring range` when `locations` is empty, answers 500 and ends the program; the Go-native version joins the locations with `,` and sends the redirect with an empty `Location` header (<https://github.com/ballerina-platform/ballerina-library/issues/9853>).
- **HTTP/1.0 falls back to HTTP/1.1 at runtime.** `HTTP_1_0` is present in the `HttpVersion` enum for jBallerina contract compatibility. When used, the Go runtime prints a warning to stderr and transparently upgrades the connection to HTTP/1.1, because Go's HTTP client cannot send HTTP/1.0 requests.
- **Trailing headers are not modelled.** The `TRAILING` header position constant is accepted at compile time for API compatibility, but all header operations (`getHeader`, `getHeaders`, `hasHeader`, `getHeaderNames`) act on transport (leading) headers at runtime. HTTP trailers sent by the server are silently discarded.
- **TLS protocol name has no effect.** The `protocol.name` field accepts `"SSL"`, `"TLS"`, and `"DTLS"` at compile time, but only TLS is supported at runtime. `"SSL"` and `"DTLS"` values are ignored because Go's standard TLS stack does not expose separate SSL or DTLS stacks.
- **`poolConfig.waitTime` maps to `ResponseHeaderTimeout`.** jBallerina's `waitTime` limits how long a request waits for a connection. In the Go runtime this is approximated by `ResponseHeaderTimeout` (maximum time to wait for the first response byte). True connection-wait limiting is not available in Go's `net/http` transport.
- **`responseLimits.maxStatusLineLength` is not enforced.** The value is accepted and validated (must be ≥ 0) but has no runtime effect. Go's HTTP transport does not expose a configurable maximum status line length (unlike jBallerina's Netty `HttpClientCodec`).
- **Proxy DNS resolution is lazy, not eager.** In jBallerina, `ProxyConfig.host` is DNS-resolved at client creation time, and an unknown hostname causes an `error` from `new http:Client(...)`. In the Go runtime, DNS resolution is deferred to the first request that uses the proxy. A bad proxy hostname does not fail at init time.
- **A nil target type discards the payload.** jBallerina routes a `()` target through the string payload builder, so a non-empty body is handed back as a `string` even though `()` was requested. The Go-native version returns `()` and drops the body, keeping the bound value inside the requested type.
- **Reason phrases are the registered ones.** jBallerina reports the reason phrase the server actually sent, both in status-code error messages and in `http:Response.reasonPhrase`. The PAL transport contract surfaces only the status code, so the Go-native version derives both from the status code's registered phrase (for example `Not Found` for 404). A code outside the IANA registry — 499, which nginx sends for a client-closed request, among others — has no registered phrase, and the phrase becomes `status code <code>` rather than being left empty.
- **A status error with an absent body keeps its reason phrase.** jBallerina extracts the error response body with the builder its `Content-Type` selects, and an extraction failure replaces the reason phrase with `http:ApplicationResponseError creation failed: <code> response payload extraction failed`. A 4xx or 5xx sent with `Content-Type: application/json` and no body at all trips that path, because a JSON decoder rejects an empty document. The Go-native version treats an absent body as having no payload, so the message stays the reason phrase and the error detail's `body` is `()`.
- **Request targets are percent-encoded, where jBallerina leaves them mostly raw.** jBallerina builds the request target by string concatenation and lets Netty encode only the space, so a path or query value carrying a delimiter changes the request's meaning — `q=a&b=c` arrives as two query parameters, the resource path segment `"a/b"` arrives as two segments, `"a?b"` starts a query string, and `"a%b"` goes out raw and is rejected with a 400 by a jBallerina listener, and `<`, `>`, `"`, `|`, `\`, `^`, `` ` ``, `{`, `}` and non-ASCII bytes go out raw in a technically invalid request line. The Go-native version percent-encodes every byte of a resource path segment outside RFC 3986's `pchar` set (so `/`, `?`, `#`, `%`, space and non-ASCII bytes are escaped, while sub-delims such as `,`, `;` and `=` go out raw as in jBallerina) and escapes query keys and values with `url.QueryEscape`, so a delimiter inside a value stays inside that value (`c->/p/["a/b"]` sends `/p/a%2Fb`) and every target is a valid URI. Two consequences: a space in a query value becomes `+` rather than `%20`, and on the remote methods, whose string `path` is sent as written, a literal `%` that does not begin a valid escape (`/a%b`) makes Go's URL parser reject the path, returning an `error` where jBallerina sends it raw; a resource path segment `"a%b"` is escaped to `a%25b` instead. This is a deliberate choice of the stricter behaviour over byte-level parity, and is open to revisiting if a real client depends on jBallerina's raw form.
- **Path and query values use Ballerina's `toString`, not Java's.** jBallerina renders a path segment or query value with Java's `String.valueOf`, so a `float` goes out as `1.0E10` and `1.0E-7`, the same as its `float:toString`. This port's `float:toString` gives `1e10` and `1e-7`, and every segment and query value follows it; `int`, `boolean`, `decimal` and `string` are unaffected and match jBallerina exactly. This keeps one rendering rule across the language and the library, and is open to revisiting.
- **Invalid resource signatures are reported per request.** jBallerina's compiler plugin rejects an invalid resource signature at build time — an ambiguous default payload parameter, an unsupported query or header parameter type, two `http:Request` parameters, more than one http annotation on a parameter, or `@http:Payload` on a `get`, `head`, or `options` resource. The Go-native version has no compiler plugin, so the program builds and each request reaching such a resource is answered with 500 and the compiler plugin's diagnostic text as the message. The default payload parameter is likewise inferred at request time, so it also applies to resources of a service object constructor, which jBallerina's plugin leaves alone.
- **Parameter binding errors use the runtime's conversion wording.** jBallerina's payload, query, and header binding failures carry `data.jsondata` and Java parser messages and name types as declared (for example `incompatible type found: 'Person'`). The Go-native version reports the message of the `lang.value:cloneWithType`-equivalent conversion and of Go's JSON, XML, and URL parsers, and prints types structurally (for example `'{| age: int, name: string, never... |}'`), because runtime types carry no declared names. The status codes, the message prefixes, and the binding outcome are unchanged.
- **`gracefulStop` waits for in-flight requests to drain.** In jBallerina, `gracefulStop` effectively behaves like an immediate stop — it returns promptly without waiting for active requests, so calling it from within a resource on its own listener succeeds. The Go-native version implements the `http:Listener` contract literally and blocks until in-flight requests complete or the graceful-stop timeout (default 60s) elapses. A resource that calls `gracefulStop` on the listener serving it therefore self-deadlocks until the timeout elapses and then returns an error, rather than succeeding.
- **A multipart part that cannot be encoded fails the send.** jBallerina writes a part whose Content-Type names an unsupported charset (for example `charset=bogus-cs`) as-is. The Go-native version encodes each part in its charset when the message is sent, so a client call returns `failed to encode multipart body: <charset>` and a listener answers a returned `Response` holding such a part with a 500 carrying the same message.
- **A multipart body set on an outbound message is decoded.** jBallerina's `getBodyParts()` decodes only an inbound body, so on a `Request` or `Response` whose body was set with `setTextPayload` or `setBinaryPayload` it returns an empty `mime:Entity[]`. The Go-native version decodes such a body too, so a well-formed one yields its parts and one holding no part returns an error, as an inbound body does.
- **Malformed percent-encoding in a form body returns an error.** jBallerina's `getFormParams()` panics with a Java `IllegalArgumentException` (`URLDecoder: Illegal hex characters in escape (%) pattern`) on a body such as `a=%ZZ`. The Go-native version returns the `form data decode failure` error that jBallerina's `getFormParams()` declares for a decode failure, with the decoding error as its cause.
- **A listener whose private key does not match its certificate fails `start`.** jBallerina accepts a valid certificate file paired with a valid private key from a different key pair at both `init` and `start`, and the listener then fails every incoming TLS handshake, so clients see only `SSL connection failed` errors. The Go-native version returns a `GenericListenerError` from `start` (`Listener.start: X509KeyPair: tls: private key does not match public key`) and serves nothing (<https://github.com/ballerina-platform/ballerina-library/issues/9908>).
